## 名词速查（不懂就看这里）

- 档位（T0/T1/T2）：这活有多重。T0 小改直接做；T1 一个功能；T2 多层、要动数据或外部系统。
- 准话：把你的口语需求翻成 AI 和人都不会误会的准确说法。后面找代码位置、写方案、定验收点都按它来。
- 访问用户：AI 主动采访你，问代码里查不到、又影响做法的背景，不用你猜它怎么想。
- 术语表：记录「这个项目用到了哪些术语」的外置文档，放在项目文件夹里，不放进技能目录。
- 垂直切片：从界面一路穿到数据的一小条完整功能，做完就能真的用，不是只搭个空架子。
- 契约：两段代码之间说好的输入、输出和出错方式。改了它就等于改了别人依赖的东西。
- 根因：真正出错的那一处。修根因是改病因，修症状是把报错压下去。
- 回归：改完之后回到最初那个症状，确认它真的好了。
- 回读：去目标那头（远端仓库、线上环境、交付文件）再看一次，确认改动真生效了。
- lint / 类型检查：程序自动查代码规范和类型是不是写错了。
- worktree：同一个仓库的另一个工作目录，共用一份历史。
- 证据：你真的跑过的命令、看到的退出码和输出，不是「应该没问题」。
- 点改卡：五句话把一个小改动说清——改哪、进出什么、出错怎么办、不碰什么、怎么算好。只在对话里说，不落文件。
- 待定节点：架构图上标着 `?` 的地方，表示「还没想清」；不用假设糊过去，等下一轮再定。
- 储备区（`fog`）：以后可能做、但现在不插队的想法。记在图里，不影响当前主线。
- 最小闭环：一条从头到尾能真正跑通的最短路径。先让它跑起来，再往上加东西。
- `.arch/`：项目的本地架构状态目录（图、看板、踩坑记录），默认不进 git。

## 取舍规则（每趟先做这一件事）

1. 定车道：这次属于哪一档、哪一类，见 SKILL.md 的车道表。
2. 逐条过技能，判「这次用得上吗」。用不上就不读、不写进本次记录，也不要为了走全流程硬凑。
3. 告诉用户结论：这次用哪几个、哪几个不用、为什么。一句话就够。

| 技能 | 什么情况用 | 什么情况不用 |
| --- | --- | --- |
| oil-explore | 目录陌生、要摸清调用链，或要盘点可复用组件 | 这个项目你天天在改，结构早清楚 |
| oil-plan | T1/T2：要把验收点和步骤定下来 | T0 小改，写方案纯属浪费 |
| oil-frontend | 要动界面、交互、前端状态与样式组织 | 纯后端、只改配置文件 |
| oil-code-review | T2 或多层改动，改完要按风险审一遍 | 一次文案改动 |
| oil-govern | 文档、规范、测试分层、worktree 乱了 | 平时的一次功能改动 |
| wf-github-ops | 要整理本地 git、传仓库、发版本 | 只想提交一个改动 |
| git-ship | 你明确要走分支加 PR 再合并 | 默认的直接提交 |
| oil-delegate | 要把整件事交给别的命令行 Agent 跑 | 自己就能做完 |
| vibehub | 第 1 步：表述模糊时把需求翻准、术语讲清 | 表述已经够清楚 |
| webapp-testing | 第 6 步：web 界面要真开浏览器验证时 | 非 web 项目、没有界面 |
| arch-grower | 面改/大改：结构说不清、要定契约、拆任务卡或出看板 | 点改、改法已清楚、只改文案样式 |
| wf-design | 涉及「好不好看」 | 只关心能不能用 |

## 底座（默认全走，按车道裁剪）

表里没单列的 `oil-bug-fix` 属于车道 4：只在原因还没查清时用；原因和改法已经明确，就按 T0 直接修，不硬走缺陷流程。

`oil-delegate` 也不是默认动作：Codex 里先用宿主自带的子 Agent；只有确实要换一个外部 CLI、并且它已经配置好 runner 时才用它。

### 步骤 1 · 需求翻译

什么时候走：新项目、新功能起步默认会走到；其它任何时候只要你的表述模糊（口语、缺主语、范围不清）就走。表述已经清楚：一句复述带过，不硬翻。

怎么做：

- 把需求翻成「准话」——可以直接对 Agent 说的准确说法。保留你的原意、语气和约束，不擅自加技术方案。
- 该翻都翻、不硬加戏：有几个模糊说法就覆盖几个，你已经清楚的词不重复教。一段里模糊点超过 5~6 个：先建议把需求切小，别一口气全翻。
- 术语统一走 vibehub 词条：拿标准名 + 一句话解释 + 内链；词条里查不到，就用最通用的叫法并注明。术语挑选和解释的规矩按 vibehub 自己那套来。
- 术语显示自动切：1~2 个 → 句内加小括号轻注；3 个以上 → 句子保持干净，术语放回复末尾「术语小注」块。
- 把用到的术语记进项目的 `docs/术语表.md`（没有 docs 就放项目根目录）。每条四样：术语（中英）/ 人话 / 词条链接 / 本项目用在哪（实现后补文件位置）。同一个词不重复记；平时随手抓到的术语也补记。
- 采访与术语表的做法参考了 mattpocock 的 grill 系技能和 addyosmani 的 interview-me（只吸收思路，未安装）。

停下来：准话没被确认前，不进后面的步骤。你说「直接做」时：复述一句 + 记下假设，跳过追问。

判据：用户能从准话里认出自己要的东西；模糊点都有归宿（翻掉、切走或记成假设）。

### 步骤 2 · 摸现场（看代码 + 访问用户）

**2a · 看代码**

大仓库或陌生仓库，把探索拆给只读子 Agent：它只回调用链、可复用组件和局部快测命令，不把大段代码塞回主上下文。Codex 里用原生子 Agent；`oil-explore` 负责给它们分工和模板，两者不冲突。

```bash
git -C <项目> status --short
git -C <项目> log --oneline -10
```

- 先把「这次要改的」和「用户自己还没提交的」分开。看到不认识的改动先问，不要替他清理、回退或暂存。
- 找适用的 `AGENTS.md`、README，以及和当前框架、当前版本精确匹配的文档；不要凭目录名猜技术栈，也不要套用记忆里的旧 API。
- 目录大或不熟时用 oil-explore 做只读盘点（它自带脚本），不要自己读完所有文件。
- 顺带把准话里的说法对到代码位置：用户说的「下载按钮」对应哪一处；对不上，就变成 2b 的问题问回来。

**2b · 访问用户（AI 采访你）**

- 只问「代码里查不到、又会改变做法」的空白；代码能查到的绝不拿来问。
- 先扫一眼代码再问，问题带着现场问：「项目里已经有个 X，你是要改它还是新加？」
- 默认一轮问完：小活 1~2 个、大活最多 5 个。T0 免访，真卡住才问；T2 或你点名「细问」时，可以切成「一次一问」慢慢磨。
- 问题库初版：给谁用 / 为什么做 / 以前怎么凑合的 / 有什么不能碰 / 做到什么程度算够。
- 问完给一段「我了解到的背景」让你核对；对上后写进项目 `AGENTS.md` 的「项目背景」小节（没有 AGENTS.md 就建一个精简的；背景很长时详细版放 docs/，AGENTS.md 里留一行路标），并从那里指一行到术语表——以后的新会话和别的 AI 能一眼接上。

判据：能说出要改哪几个文件、入口在哪、跑起来需要什么命令；背景摘要过了你的眼。

### 步骤 3 · 定档与边界

- 定档：T0 / T1 / T2，见 SKILL.md 的车道表。拿不准先按 T1。
- 把「做完」写成能看见的行为：谁用、从哪进、输入什么、出来什么、几个关键状态怎么变。验收点从准话里来，不另起一套。
- 明确写清不做什么，以及不能碰的东西（兼容性、数据、权限、性能、成本、设备）。
- 只有会改变用户可见行为、数据安全、认证策略、付费或外部副作用的信息才问，其余用仓库现状做最小假设并在回复里说出来。
- T1/T2 用 oil-plan 走它的分级与方案；T0 免仪式，在对话里说一句要改什么就行。

判据：验收点最多五条，用户读完能点头。

### 步骤 3b · 结构草图与呈现

只在这块「怎么拼」还说不清时走；改法清楚的 T0 直接跳过，别为了走流程硬画图。

先记住三条，因为服务对象是非专业用户：

- 不考专业题：架构、库、协议、参数由你按最佳实践定，只问用户能感知的后果。
- 不拿图当交付：图是内部状态；给用户的是人话「施工单」和能看见的验证结果。
- 出问题你先查：用户只描述现象，复现、读报错、定位原因都由你做完再汇报。

先决定用户要不要看图：不看图就不做卡；要看整体，再选配方。

| 形态 | 判断 | 先给用户看什么 | 内部要不要图 |
| --- | --- | --- | --- |
| 点改 | 1 个文件、1 处行为，不动接口 | 对话里说清五句话，不建图、不落文件 | 不要 |
| 面改·简单 | 2~5 个文件，但不跨模块 | 施工单 | 不要 |
| 面改·跨模块 | 动了 2+ 模块或 1 条数据流 | `project-map` + 施工单 | 需要长期契约时再用 `arch-grower` |
| 大改 | 新项目、6+ 文件、登录/支付/权限/迁移/外部集成 | `project-map` + 施工单 + 分步计划 | 复杂时用 `arch-grower` 内部存图 |

拿不准按面改走；做起来发现牵连更多，再升到大改。

**点改卡**：只在对话里说，不建文件。

```text
改哪：
进来什么 / 出去什么：
出错怎么办：
不碰什么：
怎么算好：
```

**面改/大改施工单**：开工前给用户看，只用日常话，不贴图、不讲术语。

```text
这次做什么：
第一片先做：
- 从哪进 / 中间经过 / 从哪出：
- 出错时：
不碰：
怎么算好（最多三条）：
还没定：
我替你假设的：
```

**要给用户看整体：project-map**

- 先选内容配方：路线图、模块图、状态表、问题看板、进度、方案对比。
- 再选风格皮肤：清纸(默认)、雾蓝、便笺;只做亮色,不跟随系统暗色。
- 没有默认配方；按用户现在要看什么决定。
- 输出内联卡片;需要留档时放 `projects/<name>/outputs/项目地图.html`。卡宽 768px,正文区超过 520px 时内部滚动。
- 配方和皮肤清单见 `project-map` 的 `SKILL.md` 与 `references/`。

**需要内部状态时：arch-grower**

只有大改或跨模块契约才用；普通面改跳过这一节。用包装器调用引擎（引擎在 magpie 库，包装器会自动找到它）。

```bash
py -3 <技能目录>/scripts/arch.py --root <项目> init --seed "一句话需求"
py -3 <技能目录>/scripts/arch.py --root <项目> focus
py -3 <技能目录>/scripts/arch.py --root <项目> collapse --node entry_input --label "拍照上传" --spec "小程序拍照上传" --stage "S1 采集"
py -3 <技能目录>/scripts/arch.py --root <项目> add-node --node fog_bank --label "银行流水导入" --spec "以后再做" --status fog
py -3 <技能目录>/scripts/arch.py --root <项目> export-task --node <节点>
py -3 <技能目录>/scripts/arch.py --root <项目> export-ui
```

- `init` 只在大改或需要长期契约时跑；没有 `.arch` 才初始化；包装器发现已有图会拒绝，确认要重画才加 `--force`（先备份）。初始化成功后会自动把 `.arch/` 写进项目 `.gitignore`。
- 每轮只问一个后果。先给推荐，再把 A/B 翻成人话（你会看到什么、付出什么），允许用户只回「你定」。
- 主干没有待定节点就是最小闭环。先实现那一条，跑通再补分支和储备区。
- 发散的念头进 `fog`，不插队；试错失败写进 `.arch/graveyard.md`，回复里说一句「这条试过不行」。
- 看板默认不发布。只有用户点名、或要给别人看时才加 `--publish`；要长期打开才 `arch.py dashboard on`。
- 要把整体结构、进度或问题画给用户看，交给 `project-map`：一个主配方 + 一个风格皮肤，按内容选，不要固定模板。
- 收口先给施工单：做了什么、怎么验证的、哪些还没定。看板只是附带的快照，不是交付物。
- 看板是 `graph.json` 的只读快照；图改了要重新 `export-ui`。
- 架构图只解决「结构」，不替代第 4~7 步：复用、实现、验证、收口照常走。
- 它提升的是：边界更清楚、契约更早暴露、第一片更早跑通、踩过的坑不重走。
- 它不提升：代码本身对不对、测试够不够、性能好不好——那些仍靠第 6 步和车道 4。

判据：点改能一句话填满五格；面改/大改能指出「第一片从哪到哪」，有一张按内容选的图或施工单，并说清哪些还没定、哪些进了储备区。

### 步骤 4 · 先找可复用的

- 写新代码前先搜一遍同类实现、组件、测试、脚本、依赖用法和提交历史，例如 `rg "关键词" --glob "*.ts"`。
- 机械事实交给程序：文件在不在、有几个、谁引用谁、格式对不对、类型对不对，用 rg、脚本、测试或 lint 判定，不要靠读一堆文件心算。
- 有现成模式就适配它，不新建平行的一套。

判据：能说一句「沿用了哪里的现成做法」；确实没有可复用的，说清缺什么，再写最小实现。

### 步骤 5 · 逐片实现

- 一条纵向切片穿过必要的界面、接口、业务规则和数据，做完能演示一个结果；不要只造空壳层，也别把只做了前端假数据说成集成完了。
- 先做最关键的那一片，验证过再铺开其余。
- 界面与交互交给 oil-frontend；涉及「好不好看」转 wf-design。
- 要改契约（接口输入输出、错误语义、权限、数据所有权）之前，停下问用户。
- 有行为风险的改动，先写一条能失败的测试，确认它真的抓得到问题，再改实现。纯文案、生成文件、一次性原型不用强加这套。

判据：这一片能跑、能演示。

### 步骤 6 · 验证说真话

分三层，别把全量测试当快测反复跑：

1. 编码途中：只跑秒级检查（编译、类型、lint、单个测试），一次改动最多一两轮。
2. 写完：跑与这次改动相关的快测；失败就修到过。
3. 合并前：跑一次全量门禁（项目 `AGENTS.md` 的 `oil-dev` 小节，或 CI 同款命令）；构建和端到端也放这一层。

```bash
py -3 <技能目录>/scripts/run_checks.py list <项目>
py -3 <技能目录>/scripts/run_checks.py run <项目> --yes
```

- 从耗时最短、最贴近风险的那一层开始：相关单测 → 接口或数据库集成测试 → 关键端到端路径 → lint、类型检查、构建。跑覆盖风险的那一部分，不是把清单全打勾。
- 能用程序判断的验收项就写成脚本或测试，不要让模型手工扫大批文件去证明数量、格式或引用完整。
- 读完整输出、看清退出码。UI 改动要在可用环境里真打开、真点关键路径；web 界面可以挂 `webapp-testing` 用真实浏览器跑（首次使用需装 Python Playwright + Chromium）。
- 依赖真实服务但没有凭据、网络或环境时，标成「未验证」，不要伪造成功响应，也不要把 mock 说成真实集成。

判据：报告里出现的每条结论，都对应一条你真跑过的命令。

### 步骤 7 · 收口交付

- 看最终 diff：有没有超出范围、多引入的依赖、遗留的调试代码或密钥、前后端不一致、错误处理过宽。
- 说三件事：改了什么、验证了什么（命令加结果）、没做什么以及遗留风险。
- 用户没点名就不提交、不推送、不部署、不发布。

## 车道 ① · 小改直通（T0）

什么时候走：改文案、改样式、改法明确的小缺陷，不碰数据、接口和权限契约。

顺序：定位 → 改 → 跑相关检查 → 一句回报。

- 不写计划文档、不做方向比较。
- 只在文件名和改法上都清楚时才算 T0；做起来发现牵连到数据、接口或权限，立刻升到 ② 或 ③ 并告诉用户。

## 车道 ② · 单点功能（T1）

什么时候走：一个用户能感觉到的功能，边界清楚，集中在一条垂直切片。

顺序：需求模糊先翻准 → 摸现场（必要时采访你）→ oil-plan 短对齐（验收点、非目标）→ 逐片实现（界面走 oil-frontend）→ 跑检查 → 回报证据。

- 结构说不清时，先走 3b 的点改卡或迷你图；点改卡只在对话里说，不落文件。

## 车道 ③ · 全流程（T2）

什么时候走：新产品、多层改动、含登录、数据迁移、外部集成，或者取舍多、风险高。

顺序：走完整底座（1~7）→ 先建立可判定目标、契约与分步计划 → 逐片实现并逐片验证 → oil-code-review 按风险评审 → 交付说明。

- 计划按依赖排序，每项有能演示的结果和验证方式，不要把计划写成几十条微指令。
- 评审按正确性、数据安全、权限、兼容、用户体验、可观察性排序，并引用实际文件和证据。
- 核心逻辑、安全、数据迁移这些高风险部分要做独立评审；没有独立审查资源时，明确写出「未独立评审」。
- 数据库迁移先查现有结构、数据量和部署约束；破坏性变更要有明确范围和回滚方式。

- 先走 3b 建图、定契约、找最小闭环；收口默认发布 `docs/架构看板.html`。
- 图上有待定节点时，不要把待定当成已定往下写；先问，或明确写成假设。
- 只有 3 个以上可并行节点、或节点要动高风险接口时，才用 `export-task` 交给独立子 Agent/worktree；其余主 Agent 直接写。

## 车道 ④ · 故障修复

什么时候走：有明确报错或行为明显不对，而且原因还没查清。原因和改法已经明确的小修补，按 T0 直接修，不走这里。

主刀是 `oil-bug-fix`，顺序：

1. 复现：先写一条会失败的测试；写不了就留一条能重复运行的命令。没复现不下结论。
2. 找根因：以前好的用 `git bisect` 或历史对比；有错误值的从输出往回追；有正常对照的逐项缩小差异。要能解释全部现象，每一步对得上代码位置。
3. 判个例还是普遍：手滑就只修这一处；是某种写法或误解，全仓搜同类并列出清单。
4. 修源头：在坏值第一次产生的地方改；不在报错处加空值判断、try/catch、重试、sleep 挡症状。
5. 验证：第 1 步的测试通过，相关快测通过，临时日志全部删掉。
6. 防再犯：个例留回归测试；普遍问题提议写成项目内自动检查（交给 `oil-govern`），识别不了就写进 `AGENTS.md` 的审查重点。
7. 汇报：根因、因果链、引入时间、个例/普遍、改了什么、验证命令、没验证的部分。

修到高风险目录、对外接口或数据格式时先停下来问。修复涉及数据库结构、批量删除或要合入主干时,先让一个独立只读 Agent 复核影响与回滚,再请用户确认(0.1.1 的新要求)。连续两三个猜测被推翻就止损:整理已确认事实,用 `oil-delegate` 或两个全新只读子 Agent 各查一路,对照结论;回来后 `git status` 不能有变化。

## 车道 ⑤ · 已有产物收口

什么时候走：实现和验收都已经做过了，用户只是要打包、上传、推送或发布。

顺序：组装 → 一处完整性检查 → 发布 → 目标侧回读。

发版硬门禁由项目自己的脚本负责，本工作流只负责提醒：发版前先跑项目门禁；先传包并核对完整，最后再改版本检测配置；保留上一版配置，出问题能马上切回。

- 不要重新走需求、设计或全量测试；复用已有的验收证据，只补这次打包或发布新增的风险。
- 目标位置已经有文件或历史时，先核对差异和方向，避免覆盖或推反。
- 发布命令同一类失败最多主动修正一次；再失败就停下，说明原目标、已确认结果和卡点。
- 整理本地 git、传仓库、发版本交给 wf-github-ops；要走分支加 PR 再合并交给 git-ship。
- git-ship 1.1.0:合并阶段用 `scripts/wait_and_merge.py` 限时等待,不裸跑 `gh pr checks --watch`;完成判据是 PR 状态 `MERGED`,不是「已创建」或「已开启自动合并」。
- PR 合并后确认远端头分支已清理、本地回到 main 并同步;只有权限、审批或网络这类外部阻塞才交回用户。

## 车道 ⑥ · 收尾治理

什么时候走：文档和实现打架、测试跑得慢或没分层、worktree 堆积、规范散在多处。

顺序：交给 oil-govern 做体检与治理，产出治理清单。

- 先跑 `audit_repo.py` 采集事实（文档新鲜度、死链、测试分层、worktree、分支合入状态），再给结论，不凭印象整理。
- 分支看板要能回答：每个分支在哪、推没推、进没进主干、改了什么、建议合并还是清理。删除分支或 worktree 前先给依据，等用户确认。
- 项目没有 `oil-dev` 约定时，用 `dev-profile.md` 生成一份：快测命令、门禁、高风险目录、禁改目录；生成后 explore/plan/review 共用这一份。
- 适合设成每日或每周一次的定时巡检：只报告和提议，不自动删文件、不自动改规范。

- 这一步不改业务行为；发现业务问题记下来，另开车道处理。

## 项目开发约定（oil-dev）

在目标项目的 `AGENTS.md` 里留一个标题含 `oil-dev` 的小节，四个字段就够：

```markdown
## 开发约定（oil-dev）

- 快测：`pytest tests/{target} -q`
- 门禁：`make ci`
- 高风险：`src/storage/**`、`src/auth/**`、`migrations/`
- 禁改：`vendor/`、`src/generated/**`
```

写好后 explore 不用猜测试命令，plan 把快测和门禁写进派发要求，review 自动标出高风险和越界文件。没有这一节时按仓库现状判断，不要自己编一套。
