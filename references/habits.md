# 日常 Vibe Coding · 习惯与注意事项

每踩一次坑就往这里追加一条，写清「什么情况、怎么错、正确做法」。下面是初稿，用着用着按实际情况改。

## 红线

- 先复用再发明：写新代码前先搜仓库里的同类实现、测试和脚本；有现成模式就适配它，不为了「原创」引入第二套做法。
- 机械事实交给程序：文件数量、引用关系、格式和类型用 `rg`、脚本、测试或 lint 判定，不靠读一堆文件心算。
- 不覆盖用户改动：看到不认识、不是这次改的本地改动，先问再动；不清理、不回退、不擅自暂存。
- 先对齐再开工：需求模糊先翻准（第 1 步），准话没被确认前不动代码；采访只问代码里查不到的。
- 证据才算数：只报告真跑过的命令和结果；不把「写了测试」说成「测试通过」，不把 mock 说成真实集成，不把「文件生成了」说成「功能可用」。
- 外部动作有边界：改代码不等于允许 push、部署、发布、改线上数据或产生费用；用户点名了动作和目标才做。
- 停止条件：同一方法连着两次没进展就换路，三次停下报告；发布类命令同一类失败最多主动修正一次。
- 没定位就别重试：先读完整报错，确认是参数、环境、权限还是产物问题，再动手，不要换一条等价命令硬试。
- 修根因不修症状：不在没理解的补丁上再叠补丁；不把顺手重构混进这次修复。
- 不做范围外的顺手改动：想顺手改别的，先说一句，等用户点头。

## 踩过的坑

- 每个项目的检查命令不一样。先看 `AGENTS.md`、`package.json` 的 scripts、`Makefile` 和 CI 配置，别套用记忆里的 `npm test`。
- 前端只做了假数据就当成做完了。至少要有一条从界面穿到真实数据的路径跑通。
- 把「命令退出码是 0」当成「用户能用」。界面改动必须在真实环境里打开、点关键路径。
- 靠目录名猜技术栈会翻车。看到 `src` 就以为是某框架，结果项目根本不是那回事。
- 依赖版本不同，套用记忆里的旧 API 会报看不懂的错。查文档要认准当前装的版本。
- 报错信息只看最后一行就动手，常常修错地方。整段读完再定位第一个不变量被破坏的位置。
